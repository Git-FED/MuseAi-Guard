Muse Setup Protocol / MSP-1

Build the cage before the agent.

A gated sequence for a clean start: isolate the machine, install and test controls, lock the agent's rules, then introduce credentials and capabilities in small steps.

7 PHASESEVERY PHASE HAS A GATENO SKIP-AHEAD

Do not enable the agent first and hope to add controls later. Build, test, and verify the external control plane first.

00

Pre-flight / clean slate

Start from a known state before creating the VM or introducing any new credential. Revoke legacy grants, sessions, tokens, webhooks, and forwarding paths that the agent could otherwise inherit.

Gate / zero inherited authority

Confirm no credential, session, or old relay can silently grant access. If you cannot verify it, don't proceed.

01

Isolate the machine

Build from a fresh image. Disable shared folders, clipboard, and passthrough. Default-deny network egress at the host or hypervisor; keep raw credentials off the VM.

Gate / contained boot

The machine can boot and run local code, but it cannot reach the internet or shared host data.

02

Guardrails before the agent

Install the human-owned kill switch and approval queue, a tamper-evident action log, network-egress logging, file-integrity monitoring, and the egress proxy before installing the agent.

Gate / prove the stops

Test that the kill switch locks and the queue refuses unapproved actions. Record the result before continuing.

03

Lock the persona files

Version SOUL, MEMORY, IDENTITY, SYSTEM, and RULES. Store them where the agent can read but not write; keep a copy outside the VM for comparison.

Gate / write denied

Test that the agent's runtime identity cannot modify the files. Verify the baseline and ownership.

04

Introduce credentials carefully

Start with none. Add one scoped credential at a time to the proxy's protected store; never place a raw secret on the VM or in the agent context. Log each use.

Gate / least privilege

Prove the secret is not readable by the agent and that a proxy request uses only the intended scope.

05

Make the allowlist exact

Allow only the exact hostnames and endpoints the approved workflow needs. Avoid wildcards and arbitrary relays. Log DNS and denied attempts; review the list regularly.

Gate / unknown host refused

Attempt a connection to an unapproved host. It must fail and be visible in the log or alert path.

06

Enable capabilities gradually

Begin with chat-only and read-only use. Add one capability at a time, review proposals and logs, and roll back a phase after any violation.

Gate / written trail

Keep a written record of each action, approval, and denial. Expand only while the controls continue to hold.

Verification loop

Every phase proves one boundary.

This is not a checklist to tick by memory. Each gate is a claim about what the system can or cannot do; record evidence before increasing its authority.

PROJECT ROOT / VERIFICATION
# Run the project tests before enabling $ python -m pytest 90 passed # Run the audit and inspect the result $ ./scripts/audit.sh # Keep controls tight while you learn one capability → observe → review → repeat

Order is the safety property

Three rules that keep the phases honest.

Controls live elsewhere

The agent cannot approve proposals, write the log, modify credentials, change the allowlist, or unlock the kill switch.

Approval is per action

The executor re-verifies the exact payload after approval. No batch permission becomes a blank cheque.

Rollback beats negotiation

On a violation, lock the system and return to a previously verified phase. Do not expand access to work around an unexplained failure.
